# kazkar-content

Статичний каталог книжок застосунку **Казкар** (GitHub Pages).

- `catalog.json` — індекс: `books[].{id,title,baseUrl,cover,free,version}`.
- `books/<id>/` — `manifest.json` (uk, фолбек) [+ `manifest.en.json`] + `cover` + `pNN.jpg`.
- `version` книжки — **бампати при кожній правці контенту** (тексти/зображення/переклади):
  застосунок порівнює її із закешованою копією і за новішої авто-оновлює книжку у фоні.
  Порівняння **монотонне (лише вгору)**: відкат контенту (git revert) публікувати теж
  бампом версії ВГОРУ — зниження version клієнти ігнорують. Значення — ціле число ≥ 1
  (не рядок!); невалідне клієнт толерантно трактує як 1 («оновлення немає»). Відсутнє
  поле = 1. `version` каталогу — версія схеми (клієнт ігнорує).
- **Вимога до хостингу:** клієнт додає до КОЖНОГО URL ассета книжки кеш-бастер
  `?v=<version>` (щоб stale edge-кеш CDN не змішував у одній книжці ассети різних
  версій). Хост МУСИТЬ ігнорувати query-рядок і віддавати той самий статичний файл
  (GitHub Pages — так); signed-URL сховища зі строгим query зламають усі ассети одразу.
- Схема — дзеркало bundled-книжок застосунку; деталі в README основного репо.

## Публікація

Pages роздає гілку **`deploy`**, не `main` (з 2026-09-21). Робота в `main` не
запускає жодних збірок; в ефір контент іде явно, коли реліз зібрано:

    git push origin main:deploy

Причина — квота Actions storage акаунта (0,5 ГБ-міс, рахується погодинно):
кожен деплой Pages = артефакт з усім сайтом (~365 МіБ), який GitHub тримає
добу = 2,6 % місячної квоти за пуш. `deploy` дозволяє збирати кілька правок в
один реліз замість деплою на кожен коміт, а
`.github/workflows/cleanup-pages-artifact.yml` стирає артефакт одразу після
завершення деплою (лишаються хвилини замість доби). Після пушу в `deploy` не
релончити застосунок перші ~10 хв — edge-кеш CDN ще може віддавати стару
версію ассетів (див. пам'ятку про версіонування кешу в основному репо).
